# Revision literature and implementation grounding

Verified on 2026-09-24. This note applies the research skill to primary publications, author records, publisher-deposited bibliographic metadata, and versioned implementation sources. It supplies grounding for the revision; it does not report new experimental results or establish priority. The companion `revision-references.bib` adds references without changing existing manuscript files.

## Corrections that matter to the argument

1. **Disambiguate both Sieve systems.** The existing note's description of the 2017 metrics system is correct but incomplete. A separate ICWS 2021 paper is explicitly about attention-based sampling of end-to-end traces. Citing only the metrics paper excludes directly relevant prior work. [2017 original paper](https://sieve-microservices.github.io/assets/sieve-middleware-2017.pdf), [2021 IEEE conference program](https://conferences.computer.org/icws/2021/program/).
2. **Do not claim the first diagnosis-oriented sampling evaluation.** TraStrainer evaluates three downstream RCA algorithms. A new frozen, trace-only classifier can be a useful controlled endpoint, but diagnosis after sampling is already an established research question. [TraStrainer, Sections 5.3 and 5.5](https://huanghy95.github.io/files/fse24/fse2024TraStrainer.pdf).
3. **Do not claim the first formal treatment of sampling uncertainty in tracing.** Coehlo, Merchant, and Stokely derive uncertainty estimates for sampled RPC aggregates. The revision's diagnostic-retention propositions concern a different estimand. [MAD 2012 paper](https://www.usenix.org/system/files/mad12-final9.pdf).
4. **Restrict architecture-wide cost claims.** Hindsight's distributed retroactive retrieval is an explicit alternative to sending every trace to a central tail sampler. A centralized Collector experiment cannot establish the costs of all selection after execution. [Hindsight, Sections 3 and 6](https://www.usenix.org/system/files/nsdi23-zhang-lei.pdf).

### Budget and baseline qualifications

TraStrainer Section 5.4.1 repairs final sample counts to the budget: it removes excess retained traces in reverse order or adds randomly chosen unsampled traces when under budget. Its published budget curves therefore must not be described as unmodified online retention. Its discussion also explains why preserving only anomalous traces can deprive RCA algorithms of needed normal examples. [Original paper](https://huanghy95.github.io/files/fse24/fse2024TraStrainer.pdf).

TracePicker Section 5.1.2 uses only TraStrainer's diversity component because its evaluation takes traces rather than runtime metrics. It configures a 10% rate for other baselines but uses default Sieve parameters because Sieve lacks that rate interface. Some baselines are reimplementations. Thus its ranking is not a comparison of the full TraStrainer against all alternatives at identical realized budgets. This is a qualification of TracePicker's own experiment, not independently verified implementation detail of the unavailable Sieve original. [Publisher article](https://doi.org/10.1145/3729351).

## OpenTelemetry Python SDK 1.37.0

The verified release is 1.37.0/0.58b0, published 2025-09-11. Cite the pinned code for implementation claims, rather than assuming that a living specification describes every older release. [Official release](https://github.com/open-telemetry/opentelemetry-python/releases/tag/v1.37.0).

### Sampling decision and inheritance

`TraceIdRatioBased(rate)` validates a rate in `[0,1]`, sets `bound = round(rate * 2**64)`, and returns `RECORD_AND_SAMPLE` exactly when the unsigned lower 64 trace-ID bits are below that bound. Otherwise it returns `DROP`. It does not consult the parent's sampled flag to choose the decision. `ParentBased(TraceIdRatioBased(rate))` applies the ratio sampler to roots; its default delegates retain sampled local/remote parents and drop unsampled local/remote parents. This is a deterministic threshold on an ID, not a fresh independent random draw for each span. [Pinned `sampling.py`, classes `TraceIdRatioBased` and `ParentBased`](https://github.com/open-telemetry/opentelemetry-python/blob/v1.37.0/opentelemetry-sdk/src/opentelemetry/sdk/trace/sampling.py).

`Tracer.start_span` generates a new trace ID only when there is no valid parent, otherwise inheriting the parent's trace ID. It generates a span ID and consults the sampler even when the resulting span is non-recording. A drop produces a `NonRecordingSpan`; this supports reduced recording/export work, not zero instrumentation overhead. `TracerProvider` uses the supplied ID generator or defaults to `RandomIdGenerator`. [Pinned tracer/provider implementation](https://github.com/open-telemetry/opentelemetry-python/blob/v1.37.0/opentelemetry-sdk/src/opentelemetry/sdk/trace/__init__.py).

The default ID generator uses `random.getrandbits(128)` for trace IDs and `random.getrandbits(64)` for span IDs, retrying zero values. The abstract `IdGenerator` documentation says at least the lower 64 trace-ID bits should be uniformly random. A seeded custom generator should document its distribution, cross-process uniqueness, and replay behavior. Bernoulli equations still require their stated randomness and independence assumptions; calling the real SDK does not prove them for arbitrary custom IDs. [Pinned ID generator source](https://github.com/open-telemetry/opentelemetry-python/blob/v1.37.0/opentelemetry-sdk/src/opentelemetry/sdk/trace/id_generator.py).

**Revision implication:** report the actual wrapper, generator, context propagation, package pins, and export processor. Preserve the distinction between the original BLAKE2b replay gate and a new live SDK experiment. These are different mechanisms even if both approximate the same probabilistic model.

## Jaeger 1.76.0, Badger, OTLP, and query verification

Jaeger 1.76.0 was published 2025-12-03. Version 1.76 deployment documentation describes embedded Badger with the all-in-one distribution. Persistence requires `SPAN_STORAGE_TYPE=badger`, `BADGER_EPHEMERAL=false`, and explicit key/value directories on the intended persistent filesystem. The documented defaults are ephemeral. A Kubernetes `emptyDir` can retain files across a container restart but is not durable across deletion of its pod, so report the actual volume lifetime rather than calling all file-backed storage durable. [Official release](https://github.com/jaegertracing/jaeger/releases/tag/v1.76.0), [versioned deployment documentation](https://www.jaegertracing.io/docs/1.76/deployment/), [Kubernetes volume documentation](https://kubernetes.io/docs/concepts/storage/volumes/#emptydir).

The default OTLP receivers are gRPC on 4317 and HTTP on 4318 with `/v1/traces`. HTTP accepts OTLP Protobuf and JSON, not Jaeger's UI JSON representation. Query runs on HTTP port 16686; the recommended stable programmatic retrieval API is gRPC `jaeger.api_v2.QueryService` on 16685. `GET /api/traces/{trace-id}` is a documented example of the **internal**, changeable HTTP JSON interface. Using it in a version-pinned experiment is reasonable, but it must not be called a stable API. [Version 1.76 API documentation](https://www.jaegertracing.io/docs/1.76/architecture/apis/).

The versioned CLI documents a default Badger TTL of 72 hours, a five-minute maintenance interval, and a ten-second metrics update interval. Record these settings and the measurement window. A short run can measure a filesystem footprint without characterizing maintenance cycles or steady-state storage amplification. [Version 1.76 CLI](https://www.jaegertracing.io/docs/1.76/deployment/cli/).

**Revision implications, as methodological recommendations:** distinguish exported spans, backend ingestion, query-visible complete traces, and crash durability. For retrieval scoring, freeze service/time/limit filters or retrieve known candidate IDs, document retries and settling time, and score only the returned trace content. An external ground-truth ledger may identify evaluation cases but must not supply the classifier with fault labels, expected outcomes, missing spans, or unseen attributes. Record serialized bytes, filesystem logical/allocated sizes, process CPU/RSS, and query latency as separate quantities. A single embedded backend does not establish replicated production capacity or monetary savings.

## A defensible contribution statement

The following is a proposed scope statement, conditional on completing and validating the revised experiments:

> We connect explicit failure-evidence requirements to conditional sampling bounds, then evaluate their practical implications using version-pinned SDK head sampling and specified Collector tail policies. A controlled application and backend study distinguishes trace visibility, trace-only classification of injected fault cases, transport and process costs, and backend retrievability. The results describe this workload and these diagnostic tasks rather than a universal safe discard rate.

This is an empirical and methodological contribution. It does not assert a new sampling algorithm, a first diagnostic evaluation, superiority to learned samplers, equivalence to expert debugging, or production-wide cost guarantees. The formal part should present elementary probability results as foundations and prove only the manuscript's defined propositions. The empirical part should identify which measured contrast adds evidence beyond the prior studies above. Novelty remains a judgment requiring a wider literature search and peer review; the present focused audit does not establish priority.

## Follow-up: disabling Jaeger 1.76.0's own tracing

**Verified setting:** add `OTEL_TRACES_SAMPLER=always_off` to the environment of the Jaeger all-in-one process, then restart that process. The version 1.76 monitoring documentation explicitly prescribes this setting for disabling Jaeger's internal query-service traces. Scope it to Jaeger; an application sharing that environment could also consume this variable and disable the study's application tracing. [Official version 1.76 monitoring documentation, Traces](https://www.jaegertracing.io/docs/1.76/monitoring/#traces).

The source path confirms the documented behavior. `cmd/all-in-one/main.go` calls `jtracer.New("jaeger-all-in-one")`. The pinned `internal/jtracer/jtracer.go` constructs an SDK tracer provider with a span processor and resource but does not supply `WithSampler`. Its OTLP/gRPC exporter is created directly. Consequently, `OTEL_TRACES_EXPORTER=none` does **not** disable the exporter in this initialization path. `always_off` suppresses the internal spans, while the provider, batch processor, and exporter objects are still constructed; this is not proof of zero initialization overhead. [All-in-one startup](https://github.com/jaegertracing/jaeger/blob/v1.76.0/cmd/all-in-one/main.go), [pinned internal tracer implementation](https://github.com/jaegertracing/jaeger/blob/v1.76.0/internal/jtracer/jtracer.go).

Jaeger 1.76.0 pins the Go tracing SDK to 1.38.0. That SDK's `NewTracerProvider` applies environment configuration before explicit options. Its `samplerFromEnv` reads `OTEL_TRACES_SAMPLER` and maps `always_off` to `NeverSample()`, whose `ShouldSample` returns `Drop` regardless of a parent's sampling decision. Use `always_off`, not `parentbased_always_off`, which can still sample descendants of a sampled parent. [Jaeger dependency pin](https://github.com/jaegertracing/jaeger/blob/v1.76.0/go.mod), [provider environment handling](https://github.com/open-telemetry/opentelemetry-go/blob/v1.38.0/sdk/trace/provider.go), [environment sampler mapping](https://github.com/open-telemetry/opentelemetry-go/blob/v1.38.0/sdk/trace/sampler_env.go), [sampler implementation](https://github.com/open-telemetry/opentelemetry-go/blob/v1.38.0/sdk/trace/sampling.go).

**Keep ingestion enabled.** The Collector's separate startup path starts its OTLP receiver when `options.OTLP.Enabled` is true. Preserve `--collector.otlp.enabled=true` and the study's `--collector.otlp.http.host-port=:14318` setting, together with the existing storage and query configuration. These receiver settings are distinct from the internal SDK sampler. The batch processor exports only nonempty batches, so suppressing internal spans removes those span-export attempts without disabling reception of externally generated traces. [Collector receiver startup](https://github.com/jaegertracing/jaeger/blob/v1.76.0/cmd/collector/app/collector.go), [receiver flags](https://github.com/jaegertracing/jaeger/blob/v1.76.0/cmd/collector/app/flags/flags.go), [versioned HTTP receiver flag](https://www.jaegertracing.io/docs/1.76/deployment/cli/), [SDK batch export condition](https://github.com/open-telemetry/opentelemetry-go/blob/v1.38.0/sdk/trace/batch_span_processor.go).

This follow-up verified source and documentation only. It did not run a Jaeger process or a workload. The pilot rerun should confirm ingestion on port 14318 and absence of internal trace-export timeout warnings before measurements resume.

## Calibration implementation reference

The pinned [SciPy 1.16.2 chisquare documentation](https://docs.scipy.org/doc/scipy-1.16.2/reference/generated/scipy.stats.chisquare.html) identifies the implemented Pearson multinomial goodness-of-fit test, its independent-observation null, and the default k minus one degrees of freedom when no parameters are estimated. It cautions about small bin counts and describes the chi-square approximation. The manuscript uses five merged bins and zero fitted parameters, and explicitly calls these p-values asymptotic. Holm adjustment does not remove that approximation or prove independence of deterministic hash decisions. Checked on 2026-09-24.
