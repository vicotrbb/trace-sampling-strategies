# Setup amendments before measured execution

2026-09-25: The planned full-retention pilot completed at 50, 2,000 and 8,000 traces/s. At 8,000, Collector CPU was 1.90 seconds over the fifteen-second measurement/drain interval, below the predefined 0.25-core criterion. The permitted 20,000-trace/s pilot used 4.62 CPU seconds (0.308 cores), with maximum scheduling lag 3.53 ms and all counters reconciled. The measured rate list is therefore fixed to 50, 2,000, 8,000 and 20,000 traces/s, giving 80 cells across four policies and five blocks.

Before the measured freeze, an additional functional pilot checks head10, tail10 and tail100 at the selected maximum rate. This checks whether sampler buffering/export can keep up at the intended pressure. It is excluded from estimates and does not select policies based on a favorable effect. The source gains an explicit pilot-policy option; measurement code and policy settings are unchanged. The separate diagnosis pilot verifies raw observed timings and parent structure; full-data accuracy is not an acceptance criterion and will not tune the fault parameters.

All three high-load sampler functional pilots completed at 20,000 traces/s with reconciled delivery. Tail10 used 7.35 CPU seconds and tail100 used 8.97 over fifteen-second intervals; maximum scheduling lags were 56.35 and 33.48 ms. These pilot values remain excluded. The measured archive uses gzip level1 only after the CPU endpoint to reduce archival time; uncompressed JSON is the reported byte endpoint. No timing, sampling or load rule changes. Diagnosis collection and replay run before the load campaign so the two workloads do not overlap. The final orchestration script records each stage and stops on a failed stage.
