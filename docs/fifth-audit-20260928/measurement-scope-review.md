# Generator and save-counter scope

Reviewed during measured collection, before analyzing the complete treatment grid. No workload, acceptance rule, endpoint, or frozen file was changed.

The protocol's phrase "external generator/gate CPU is separately observed" is broader than the recorded quantity. The frozen implementation prepares all payloads, including the pre-ingress hash selection, before starting Collector or Jaeger. Its generator endpoints cover HTTP sending, scheduling, and monitoring only. They do not time input construction or the gate's hash work. The protocol separately specifies excluded preparation; the active manuscript and README now make this boundary explicit. The primary Collector, Jaeger, and process-sum comparisons are unchanged. Neither the measured generator quantity nor their sum is presented as total instrumentation or fleet cost.

The Jaeger save counter is updated after `WriteTraces` returns in the pinned source. Matching it to supplied selected spans establishes the successful-save observation used in acceptance. It does not establish crash durability, exhaustion of later compaction work, or complete backend attribute fidelity. Full JSON reconstruction, save counts, and the backend content sample are separate evidence checks. Subsequent trace queries and shutdown are outside the process-CPU window.

The higher-load batching study preserves application fields but changes trace identities, timestamps, and study attributes, and increases tail capacity relative to the older low-load configuration. Within each campaign, paired treatments receive identical bytes and have common limits. Comparing the two campaigns describes whether the earlier sign persists at the new operating point; it does not isolate offered rate as the sole intervention.
