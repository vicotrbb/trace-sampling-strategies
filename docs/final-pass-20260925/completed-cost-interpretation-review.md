## Required wording clarifications

1. **Name the reference control in the abstract and conclusion.** The reversal is in the retain-all tail-minus-bypass contrast, not in absolute tail CPU as timeout rises. In the dual-export arm, mean tail CPU decreases from 0.43000 to 0.39125 s, while bypass decreases from 0.60250 to 0.32500 s. Consequently, the contrast changes from -0.17250 to +0.06625 s. Add “relative to the corresponding bypass control” to both compact claims. The detailed results already identify this estimand correctly. [Completed cost summary](/Users/victorbona/Code/Research/trace-sampling-strategies/data/derived/final-cost-20260925/cost-summary.json).

2. **Qualify the abstract's opening generalization.** Change “Trace sampling reduces export volume” to “Trace sampling can reduce export volume,” or explicitly restrict the statement to dropping records. Retain-all tail increases measured JSON volume from approximately 4.99 to 7.05 million bytes in this experiment. The existing opening otherwise sounds unconditional despite the paper's own counterexample. [Serialization inspection](/Users/victorbona/Code/Research/trace-sampling-strategies/data/derived/final-cost-20260925/serialization-inspection.json).

## Source and measurement agreement

- **Decision cadence and forwarding:** the pinned implementation sets the default policy ticker to one second, takes an eligible decision batch on a tick, loops over trace IDs, and forwards each sampled trace separately to the next consumer. This supports the result paragraph's explanation for the configured tail-to-batch pipeline. Prefer “uses a default one-second policy ticker” to avoid implying a one-second decision latency or a strict execution deadline. The configured decision wait remains separate. Upstream explicitly warns that slow evaluation/downstream processing can delay decisions. [Initialization and decision loop, v0.136.0](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.136.0/processor/tailsamplingprocessor/processor.go#L154), [forwarding](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.136.0/processor/tailsamplingprocessor/processor.go#L680), [slow evaluation guidance](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.136.0/processor/tailsamplingprocessor/README.md#slow-sampling-evaluation).
- **Grouping:** `groupSpansByTraceKey` separates spans by trace ID, and `appendToTraces` creates new resource and scope containers while copying span content. The observed 600 versus 6,000 resource groups, with the same respective numbers of scope groups, is consistent with this path. The file exporter's entry point marshals the received trace structure; that source supports serialization of received data, while the exact framing totals come from the archived outputs. Writing “600 resource groups and 600 scope groups” would remove the slash wording's minor ambiguity. [Grouping implementation](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.136.0/processor/tailsamplingprocessor/processor.go#L541), [container creation](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.136.0/processor/tailsamplingprocessor/processor.go#L712), [file exporter](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.136.0/exporter/fileexporter/file_exporter.go#L23).
- **Batch counts:** bypass has 300 batches of 50 spans at 100 ms and 60 batches of 250 spans at 1,000 ms. Retain-all tail has 60 batches except for one dual/100 ms cell with 61, so “approximately sixty” is accurate. Tail10 has 59 batches and 1,450 spans in every cell. These are measured outcomes, not a universal consequence of the configured timeouts. The batch processor supports both size and timeout triggers. [Summary](/Users/victorbona/Code/Research/trace-sampling-strategies/data/derived/final-cost-20260925/cost-summary.json), [batch documentation, v0.136.0](https://github.com/open-telemetry/opentelemetry-collector/blob/v0.136.0/processor/batchprocessor/README.md).

## Interpretation boundaries to preserve

The controlled interventions establish configuration-dependent CPU contrasts for this fixed corpus, load, versions, node, and measurement window. They do not apportion CPU among policy evaluation, allocation/copying, batch processing, JSON serialization, protobuf/gzip work, HTTP handling, or backend activity. The added export path includes these configured components; it is not merely a count of additional bytes. The pinned OTLP/HTTP documentation confirms the encoding/compression options, not a numerical cost decomposition. [OTLP/HTTP v0.136.0](https://github.com/open-telemetry/opentelemetry-collector/blob/v0.136.0/exporter/otlphttpexporter/README.md).

The manuscript already preserves this distinction by rejecting an intrinsic tail-overhead interpretation and separating the historical replay/live comparison. The conclusion's “show why” is acceptable only as an illustration that retained trace fraction is insufficient. “Illustrate why retained trace fraction is insufficient” would avoid suggesting a completed mediation analysis. Likewise, “measured JSON bytes” is more precise than unrestricted “output bytes” when referring to the structural inspection: that inspection does not measure compressed OTLP wire volume.

The explicit post-collection label is correct. `serialization-inspection.json` records a descriptive inspection of all 96 cells, additional to the frozen primary analysis. It corroborates a framing observation without converting it into a prospective endpoint or proving the CPU share attributable to framing. The [separate validation receipt](/Users/victorbona/Code/Research/trace-sampling-strategies/docs/final-pass-20260925/cost-validation.json) reports fixed content/order, native selection, CPU endpoints, backend content, zero throttled periods, and the same 3.336 ms maximum lag. This review reads that receipt rather than repeating its validation.
