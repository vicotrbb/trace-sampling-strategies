# Final source and contribution review

Checked 2026-09-25 using the research skill's primary-source workflow. This is an internal source review, not independent peer review. Scope: the current manuscript, pinned Collector source, related research, retrospective multiplicity context, and the proposed exporter/batching intervention. No workloads were run and no Kubernetes access was used.

## Defensible contribution

The defensible contribution is a reproducible, task-specific measurement study connecting explicit evidence requirements to actual retained spans and measured resource boundaries. The proposed factorial experiment can add controlled estimates for particular exporter and batching interventions. The sources do not support priority claims for diagnostic sampling evaluation, trace-sampling uncertainty, or the late-span/cache/buffer mechanisms. The current introduction already avoids most such claims; retain that restraint. A focused source review cannot establish publication novelty or acceptance.

The [v0.136.0 distribution manifest](https://github.com/open-telemetry/opentelemetry-collector-releases/blob/v0.136.0/distributions/otelcol-contrib/manifest.yaml) pins the tail sampler, batch processor, file exporter, and OTLP exporters to v0.136.0. Cite these versioned sources rather than current `main` documentation when interpreting this experiment.

One implementation detail matters when explaining the cache: a successful cache insertion causes `releaseSampledTrace` or `releaseNotSampledTrace` to remove the trace from the internal map immediately. Without a configured cache, the decided entry can remain there until buffer removal. Avoid describing both paths as identical except for an additional cache consulted after eviction. [Release implementation](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.136.0/processor/tailsamplingprocessor/processor.go#L690).

The early root ERROR intervention changes the evidence available at decision time. Its benefit here follows from the selected status policy and known marker placement. It does not establish that production failures reliably set an early root error or that caches universally improve diagnosis. Cite the pinned source directly in the probe discussion and describe the probes as measured consequences of documented behavior.

## Known cost mechanisms and the prospective intervention

Generation, transport, aggregation, analysis, and storage are already recognized as distinct tracing costs. Sifter explicitly contrasts where head and centralized tail sampling avoid work. Hindsight demonstrates a different architecture that buffers locally and retrieves traces after triggers, so full central ingress is not an inherent property of every retrospective selection method. [Sifter, Sections 2.2 and 2.3](https://vaastavanand.com/assets/pdf/lascasas2019sifter.pdf), [Hindsight, NSDI 2023](https://www.usenix.org/conference/nsdi23/presentation/zhang-lei).

Batching effects are also documented: the batch processor supports size and time triggers, with `send_batch_size` counting spans and acting as a trigger rather than a hard maximum. The file exporter marshals each received trace batch before writing it. Consequently, equal retained span counts need not imply equal serialization calls, framing bytes, compression work, or CPU. [Batch README v0.136.0](https://github.com/open-telemetry/opentelemetry-collector/blob/v0.136.0/processor/batchprocessor/README.md), [file export implementation v0.136.0](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.136.0/exporter/fileexporter/file_exporter.go#L23).

The proposed 2 exporter paths x 2 batch timeouts x 3 sampler settings is a useful intervention. For fixed timeout, the paired contrast

`[CPU(tail10,file+OTLP) - CPU(bypass,file+OTLP)] - [CPU(tail10,file) - CPU(bypass,file)]`

estimates how adding the specified export path changes the tail-versus-bypass CPU difference in this workload. It is an interaction between defined configurations. It does not identify an intrinsic tail-sampler overhead or prove the cause of the earlier replay/live sign reversal. Use CPU seconds for this contrast, not differences between percentages with different denominators.

Before freezing the protocol:

1. **Keep tail100 interpretable.** Preserve policy order and explicitly keep `sample_on_first_match: false`. Tail100 versus bypass retains the same span set but includes buffering, policy evaluation, changed forwarding granularity, and downstream consequences. The pinned processor evaluates decisions on a one-second ticker and forwards each retained trace separately. [Initialization](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.136.0/processor/tailsamplingprocessor/processor.go#L154), [decision loop](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.136.0/processor/tailsamplingprocessor/processor.go#L392), [policy loop](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.136.0/processor/tailsamplingprocessor/processor.go#L469).
2. **Freeze the entire added path.** Record OTLP transport, encoding, compression, retry, queue size/consumers, and exporter-helper batching. OTLP/HTTP defaults include protobuf encoding and gzip compression; the helper has asynchronous queueing and retries, with its additional batching disabled unless configured. These are part of the treatment, not implementation details that can be omitted. [OTLP/HTTP v0.136.0](https://github.com/open-telemetry/opentelemetry-collector/blob/v0.136.0/exporter/otlphttpexporter/README.md), [exporter helper v0.136.0](https://github.com/open-telemetry/opentelemetry-collector/blob/v0.136.0/exporter/exporterhelper/README.md).
3. **Verify the batching manipulation.** Fifty five-span traces per second yield 250 spans/s, close to the proposed 256-span trigger and one-second timeout. Report actual batch-size and timeout-trigger counts, not just settings. The byte-size histogram requires detailed telemetry; keep telemetry settings and scrape schedules identical. [Pinned batch metric definitions](https://github.com/open-telemetry/opentelemetry-collector/blob/v0.136.0/processor/batchprocessor/metadata.yaml).
4. **Reconcile the fixed CPU window.** Check warmup completion before the measured start, final retained IDs/spans, exporter failures, queue/buffer state, and whether all intended exports finish inside the common drain. A five-second drain is a design choice, not a guarantee. Preserve failures or unfinished cells; do not silently extend only their CPU windows. Common timestamp translation must preserve durations and attributes; archive the translated serialized-input hash and use identical bytes across treatments. Separate warmup and measured IDs in receipts.
5. **State the inference unit.** Eight randomized runtime blocks on one archived corpus assess repeatability conditional on that corpus and the controlled replay schedule. They do not create eight independent workloads or new diagnostic datasets. Launching Jaeger in both exporter arms holds process presence fixed but not ingestion work, which is intentionally changed. Keep its internal tracing disabled, preserve all block outcomes, and report observed contrasts even if intervals span zero. [Jaeger 1.76 monitoring guidance](https://www.jaegertracing.io/docs/1.76/monitoring/#traces).

## Related work without an irrelevant algorithm ranking

| Primary work | Accurate comparison and boundary |
| --- | --- |
| [Sifter, SoCC 2019](https://vaastavanand.com/assets/pdf/lascasas2019sifter.pdf) | Learns common trace structure and favors poorly represented executions. Retention utility and sampler efficiency are established topics, so this paper should not claim to introduce them. |
| [Sieve, ICWS 2021, official program](https://conferences.computer.org/icws/2021/program/) and [STEAM, ESEC/FSE 2023, authors' record](https://www.microsoft.com/en-us/research/publication/steam-observability-preserving-trace-sampling/) | Both are directly relevant trace-sampling work. The 2021 Sieve is distinct from the 2017 metrics system. Exact Sieve cost claims remain outside this review because its original full text was unavailable; STEAM's abstract does not support converting throughput into infrastructure savings. |
| [TraStrainer, FSE 2024, Sections 5.3 to 5.7](https://huanghy95.github.io/files/fse24/fse2024TraStrainer.pdf) | Evaluates downstream RCA Top-1/Top-3 accuracy and MRR, so diagnosis after sampling is not new. Its budget evaluation repairs sample counts, and its sampler timing excludes the separately running metric-preference extractor. Those boundaries differ from the current study. |
| [TracePicker, FSE 2025, Sections 3 and 5](https://doi.org/10.1145/3729351) | Measures anomaly recall, type coverage/balance, latency-statistic consistency, and sampler efficiency. Its comparison uses only TraStrainer's diversity component and Sieve's default parameters rather than a shared configured rate. Do not treat that ranking as a full-method comparison at equal realized budgets. |
| [Coehlo, Merchant, and Stokely, MAD 2012](https://www.usenix.org/conference/mad12/workshop-program/presentation/coehlo) | Derives uncertainty for sampled RPC aggregates. Witness retention is a different estimand, not the first formal treatment of uncertainty in tracing. |
| [Tracing-agent overhead, ICPE 2026](https://icpe2026.spec.org/preprint/Benchmarking_the_Overhead_of_Distributed_Tracing_Agents_2.pdf) | Studies Java agents with a non-distributed microbenchmark and verifies record completeness. Its lost-record findings reinforce cost/completeness reconciliation, but its timing values do not transfer to this Python/Collector/backend setup. |

No learned-sampler benchmark is required to support the bounded configuration and evidence-contract claims. Such a benchmark would become necessary for an asserted quality, efficiency, or state-of-the-art advantage over those algorithms. Keep the comparison qualitative and explicit about different inputs, endpoints, and cost boundaries.

## Retrospective Bonferroni context

The current manuscript does not contain the retrospective correction. It appears in `docs/validation-report.md`, `docs/revision-methodology-review.md`, and `scripts/analyze_revision.py`, where the multiplier 130 is hard-coded. Explain the family: seven head rates x three failure classes x five `(m,k)` strata, plus five nonzero-background tail rates x one unprotected class x five strata, giving 130 nondegenerate model checks. This does not automatically cover other inspected endpoints or subgroup searches.

Bonferroni uses a union bound and does not require independence between those tests. Applying it after inspecting results is not automatically mathematically invalid if the correction covers the complete fixed search family and each marginal test is valid. A selected or incomplete post hoc family would not support the same guarantee. Here the binomial test additionally assumes the disputed independent Bernoulli model; multiplication by 130 cannot establish that assumption. These are implications of the general inequality, not claims that NIST validates this specific historical analysis. [NIST Bonferroni method](https://www.itl.nist.gov/div898/handbook/prc/section4/prc473.htm).

Retain the historical 19/100 result and label the reported approximately 0.0007145 unadjusted and 0.092886 adjusted values as exploratory, conditional reference calculations. Do not describe the latter as confirming calibration, correcting away the discrepancy, establishing equivalence, or making the original analysis prespecified. Report why that stratum was selected. The fresh sixteen-test Holm analysis is a separate analysis with new data and its own assumptions. [ASA statement on p-values, principles 2 to 4 and 6](https://doi.org/10.1080/00031305.2016.1154108).

## Concrete current-text corrections

- In `paper/results.tex`, the sentence beginning “These replay results establish reductions in measured ingress/export work” exceeds the separated measurements. Replace “work” with “volumes” and state the observed Collector CPU/RSS changes separately. File bytes and total process CPU do not identify isolated ingress or export CPU components.
- Prefer “failure-family and operation-location classification” consistently over “cause-and-service identification” in the introduction, results table, methods, and propositions. The methods already admit that SQLSTATE 42P01 cannot distinguish a bad query from missing schema. This is a terminology correction to prevent a broader causal reading, not a rejection of the explicitly bounded endpoint.
- Do not add a claim that the matched probes discover late-span/cache/buffer failure modes, or that a future exporter/batching contrast explains the whole historical CPU sign reversal. The current text largely avoids these claims. The new experiment can support only the specified conditional contrasts once validated.

Suggested contribution sentence: “We quantify how explicit evidence requirements and documented Collector state transitions affect retained diagnostic evidence, and measure resource changes at declared boundaries under controlled, version-pinned configurations.” Add the exporter/batching intervention only after its results and validation exist.
